# v0.6 设计文档：混合路由 Agentic 检索（方案 C）

> 状态：待学习者批准
> 基线（要打败的数字）：report-20261109-152632 —— q20-q24 关键词 0/5，聚合 关键词 0.79 / hit率 0.80 / MRR 0.69，q16 生成层失守

## 1. 目标

给检索层加"题型意识"：事实题继续走单发快路径（不花冤枉钱），
聚合题走"分解-扫描-综合"慢路径（多轮检索攒齐候选全集再作答），
事实题出口加实体一致性闸门（治跨实体污染）。

**非目标**（明确不做）：通用 ReAct 循环、工具调用框架、流式改造慢路径。

## 2. 架构

```
question
   │
   ▼
┌─────────────┐   type=fact（默认，规划失败也落这里）
│  规划器       │───────────────► search() 单发 ──► 实体闸门 ──► answer()
│ (路由+分解    │
│  一次LLM调用) │   type=agg
│              │───────► 扫描执行器（预算内逐子查询检索，
└─────────────┘          候选池累积去重，停止条件见 §3.2）
                                    │
                                    ▼
                            综合器（先列全集再比较/计数，专用 prompt）
```

新模块 `rag/agent.py`，只组合现有零件；`search()`/`answer()` 契约不动。

## 3. 组件契约

### 3.1 规划器（mine）
- 单次 chat 调用，要求返回 JSON：`{"type": "fact"|"agg", "sub_queries": [...]}`
- 聚合特征提示进 prompt（最/几款/共有/哪些/分别）；sub_queries 建议按类别拆
  （"支持NFC的智能音箱有哪些" × 6 类）
- **健壮性铁律**：JSON 解析失败/超时/字段缺失 → 一律降级 `type=fact`。
  规划器死，系统退化成 v0.5，永不劣化。

### 3.2 扫描执行器（**学习者实现区**）
```python
def scan(sub_queries: list[str], settings) -> list[dict]:
    """逐子查询检索，累积候选池。返回去重后的池（按分数降序）。"""
```
- 候选池键 = `(source, chunk_index)` 去重（RRF 同款键）
- **修订（M2 验收教训）**: 每子查询 `双通道各召 16 + _rrf_fuse 取 20`，不走 rerank
  ——负锚毒在召回/融合层就把真块挤掉了，rerank 天花板(rerank_candidates=8)封死单查上限；
  聚合要召回广度，不要精排精度（还省 6 次 rerank 调用）
- 停止条件：子查询耗尽 / **连续 2 轮零新增**（垃圾重叠≠枯竭）/ 池满 96
- 墓碑注：`#raise NotImplementedError`

### 3.3 综合器（prompt 骨架 mine，调优 **学习者**）
- `answer_synthesize(question, pool)`：prompt 要求**先逐块列出满足条件的产品清单，
  再比较/计数，最后一句给结论**（列表即思维链，也给 judge 留证据）
- 引用格式与现有 `[i]` 一致

### 3.4 实体闸门（mine，事实路径出口）
- 触发：top 块来源与问题主体跨产品族（启发式：source 文件名 vs 问题词），或一律触发（v1 简化：一律触发，量化延迟后再说触发式）
- 单次 LLM 调用："问题主体与资料主体是否一致？只答 一致/不一致"
- 不一致 → 拒答（走现有拒答话术）；分数闸门在前、实体闸门在后

## 4. 失败模式 → 组件映射

| 死法 | 题 | 治它的组件 | 度量 |
|------|----|-----------|------|
| 部分扫描冒充全扫描 | q20/q22 | 扫描执行器（池攒齐再比） | 关键词 81/1276 |
| 局部证据下全称结论 | q21 | 综合器（先列全集） | 关键词 362 |
| 否定锚反转 | q24 | 扫描执行器（池扩容 13 块全进池） | hit(all) 0→≥0.8 |
| 跨实体污染 | q16 | 实体闸门 | 恢复拒答 |

备选方案记录：q24 的否定锚也可用语料侧修复（非 NFC 产品不写"NFC：不支持"行）——
语料挡箭牌能救这一题，救不了"检索集装不下"这个类；选池扩容，语料不动。

## 5. 评估目标（v0.6 验收线）

- **回归护栏**：q01-q19、q23 关键词保持 1.0，hit 不降
- **新题歼灭**：q20-q24 关键词 ≥ 4/5；q24 hit(all) ≥ 0.8
- **q16**：恢复正确拒答
- **成本**：事实题 LLM 调用 ≤ 3（规划+闸门+生成）；聚合题 ≤ 12

## 7. 里程碑

1. M1 骨架+规划器：fact 路径全通，planner 日志可见 → eval 无回归
2. M2 扫描执行器：q24 hit(all) 单项达标（0→0.8+）
3. M3 综合器：q20-q22 关键词达标
4. M4 实体闸门：q16 恢复拒答，q01-q15 无误伤
5. M5 收官：全量跑分对比基线，README/复盘 更新

## 8. 风险

- 规划器误路由：聚合题被当事实题 → 表现为不劣化（仍单发答错），靠 eval 的
  route 字段观测，不致命
- 综合器池太大爆上下文：pool_cap 48 块 × ~350字 ≈ 1.7万字，qwen 128k 无压力
- 实体闸门误伤：v1 一律触发，若 q01-q15 有误伤再收窄触发条件
